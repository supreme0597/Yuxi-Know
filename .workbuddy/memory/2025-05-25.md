# 2025-05-25

## Undo 交互优化：撤回后提示词回填输入框

- **问题**：用户撤销消息后，提示词从聊天区消失但不会回填到输入框，导致用户需要重新手打
- **修复**：`AgentChatComponent.vue` 的 `handleUndo` 中，撤销前保存 `msg.content`，撤销成功后回填到 `userInput`
- **语义**：Undo = "回退到发送前"，用户消息内容应回到输入框（类似邮件撤回到草稿箱）
- 用户可原样重发、修改后重发、或清掉不管

## Fork Bug 修复：checkpoint 克隆 PK 冲突 + blob 类型不匹配 + 消息不完整

- **问题1**：Fork 时 `INSERT ... SELECT` 克隆 checkpoints/checkpoint_writes，SELECT 直接取原表 `thread_id` 列，导致新行 PK 与原行冲突 → `UniqueViolationError`
- **修复1**：用 `literal(thread_id_b).label("thread_id")` 替代 `checkpoints.c.thread_id`
- **问题2**：`checkpoint_tables.py` 中 `blob` 声明为 `String`，实际数据库是 `bytea`；`checkpoint_writes.idx` 声明为 `String`，实际是 `integer` → Fork 插入 blob 时类型不匹配
- **修复2**：`blob` → `LargeBinary`，`idx` → `Integer`
- **问题3**：Fork 克隆消息时 `id <= message_id`，当 fork 点是 user 消息时，不包含紧随其后的 assistant 回复
- **修复3**：引入 `fork_boundary_id`，找到 fork 点 user 消息后的下一条 assistant 消息，扩展克隆边界到 assistant 回复
- **问题4**：Fork 按钮放在 user 消息上不合理，用户更直觉是在 AI 回复上 fork（"从这里走另一条路"）
- **修复4**：Fork 按钮从 human 消息移到 AI 消息（仅 status=finished 时显示），Undo 保留在 human 消息上；后端逻辑同步调整 — fork 点是 assistant 时克隆边界就是 assistant 自身
- **教训**：声明 `table()` 反射时必须对照 `information_schema.columns` 确认实际类型；Fork 应克隆完整对话轮次（user+assistant）；Fork 按钮语义上应放在 AI 回复上

## Fork Bug 修复：assistant 消息上 fork 时 checkpoint/消息边界不一致

- **问题**：前端 fork 按钮在 assistant 消息上（`getLastMessage` 取 type='ai'），但后端收到 assistant message_id 后回溯到对应 user 消息，然后 `fork_boundary_id = user.id - 1`，导致丢失该轮 Q&A（Q3+A3 都没了）。同时 checkpoint 用 `select_checkpoint_parent` 从 ckpt_out_A2 开始，AI 只记到 A2
- **根因**：原始设计假设 fork 一定在 user 消息上触发，前端改成 assistant 消息后后端没跟进
- **修复**：
  - assistant fork：`fork_boundary_id = target_msg.id`（包含 AI 回复本身），checkpoint 查 `source='output'` 找到 `ckpt_out_A3`，ancestors 从 ckpt_out_A3 开始
  - user fork：`fork_boundary_id = target_msg.id - 1`（不含 fork 点），checkpoint 通过 `select_checkpoint_entry` → parent 找到 `ckpt_out_A3`
  - 两种场景消息和 checkpoint 都对齐到同一轮次
- **核心原则**：用户在哪 fork，就 fork 哪里（含）之前的全部内容；消息边界和 checkpoint 边界必须包含相同轮次

## Fork 全部对话不可 fork 的 Bug 修复

- **问题**：改完边界对齐逻辑后，所有对话 fork 都报错 "该消息之前没有可用的 AI 推理状态"
- **根因1**：`source='output'` 的 checkpoint 在你们的 LangGraph 配置下可能不存在（取决于 `checkpoint_at` 配置），查不到就走 fallback
- **根因2**：fallback 里取 `parent_checkpoint_id` 后没有处理 `NULL`（第一轮对话的 root checkpoint parent 为 NULL），导致 `not parent_row[0]` 为 True 直接报错
- **根因3**：fallback 逻辑取 input checkpoint 的 parent 是错的——`ckpt_in_Q3.parent = ckpt_in_Q2`（状态只到 Q1+A1），丢失了 Q2+A2+Q3+A3。正确做法是找 `ckpt_in_Q3` 的**子节点**（`parent_checkpoint_id = ckpt_in_Q3` 的那条），即 `ckpt_in_Q4`（状态包含 Q1~A3）
- **最终修复**：
  - 删除 user 消息分支，fork 仅支持 assistant 消息（user 消息只有 undo）
  - assistant 分支：先查 `source='output'`，找到直接用；找不到则查 input checkpoint 的子节点（`parent_checkpoint_id = input_ckpt_id`），子节点的状态包含 A3
  - 子节点也没找到（A3 是最后一条消息）→ 用 input checkpoint 本身 + checkpoint_writes 恢复
- **核心原则**：消息边界和 checkpoint 边界必须包含相同轮次；LangGraph checkpoint parent 链的方向是向上的，要找"状态包含 A3"的 checkpoint 需要往下找子节点
